# 1\. Reporting Architecture

## 1.1 Architecture Overview

Reporting BLIPS dilayani oleh dedicated Reporting Service yang mengakses Read-Replica DB untuk avoid impact pada OLTP. Untuk reporting kompleks (mis. Roll-Forward CKPN, Stage Distribution), digunakan materialized views yang di-refresh scheduled.

> ┌────────────────────────────────────────────────────────────────┐  
> │ REPORTING SERVICE │  
> │ │  
> │ ┌────────────┐ ┌──────────────┐ ┌─────────────────────────┐ │  
> │ │ Query │ │ Export │ │ Schedule & Email │ │  
> │ │ Engine │ │ Engine │ │ Service │ │  
> │ │ (SQL+API) │ │ (Excel/PDF) │ │ (cron + SMTP) │ │  
> │ └─────┬──────┘ └──────┬───────┘ └────────┬────────────────┘ │  
> │ │ │ │ │  
> │ └────────────────┴────────────────────┘ │  
> │ │ │  
> │ ┌─────────────────▼──────────────────────┐ │  
> │ │ READ-REPLICA DB (async replication) │ │  
> │ │ + Materialized Views (refreshed daily) │ │  
> │ └─────────────────────────────────────────┘ │  
> └──────────────────────────────────────────────────────────────────┘

## 1.2 Materialized Views

| **Materialized View**     | **Purpose**                                    | **Refresh Schedule**                |
| ------------------------- | ---------------------------------------------- | ----------------------------------- |
| mvw.posisi\_portofolio    | Snapshot posisi instrumen aktif harian         | Daily 19:00 WIB (post-MTM)          |
| mvw.ckpn\_rollforward     | Roll-forward CKPN per stage per tipe instrumen | Monthly post hard-close + on-demand |
| mvw.stage\_distribution   | Distribusi exposure per stage                  | Daily 19:00                         |
| mvw.concentration\_risk   | Per counterparty/rating/tipe                   | Daily 19:00                         |
| mvw.amortization\_summary | Aggregate dari amortization schedule           | Daily 19:00                         |
| mvw.eir\_summary          | EIR awal vs current per instrumen              | Daily 19:00                         |
| mvw.fx\_position          | Posisi valas per mata uang                     | Daily 11:00 (post-JISDOR update)    |
| mvw.ecl\_summary\_period  | Aggregate ECL per periode                      | Monthly post ECL job                |

## 1.3 Output Format Standards

| **Format**              | **Use Case**                                  | **Library/Tool**                                             |
| ----------------------- | --------------------------------------------- | ------------------------------------------------------------ |
| Web Dashboard (HTML+JS) | Real-time interactive view                    | React + Recharts                                             |

## 1.4 Watermark & Metadata

Setiap export Excel/PDF WAJIB include:

  - Watermark: "GENERATED BY BLIPS — TUGURE — INTERNAL CONFIDENTIAL".

  - Metadata footer: timestamp, user yang export, periode data, parameter version (untuk re-perform).

  - Hash checksum (SHA-256) untuk file integrity.

  - Tracking: setiap export tercatat di doc\_access\_log + audit trail.

# 5\. Dashboard UI (Web Real-Time)

## 5.1 Dashboard per Role

**Treasury Dashboard:**

  - Posisi portofolio per tipe instrumen (pie chart).

  - Mutasi terkini (table 10 entries).

  - Akrual harian (line chart 30 hari).

  - Notifikasi: rating downgrade, periode closing, JT instrumen.

**Risk Dashboard:**

  - ECL Summary per stage + per tipe (stacked bar).

  - Konsentrasi per rating + counterparty (heatmap).

  - Stage migration alerts (table).

  - Counterparty rating changes (timeline).

  - MEV current values (gauge).

**Akuntansi Dashboard:**

  - Status periode buku (timeline + warna).

  - Mapping coverage (event aktif vs tidak).

  - Mapping validation (jika ada error).

  - GL reconciliation status (today, last 7 days).

  - FX rate today + history.

**CFO/Direksi Dashboard:**

  - Total portofolio value.

  - P\&L investasi YTD.

  - ECL FL total + delta vs prior period.

  - Stage distribution (current).

  - Konsentrasi risiko top 10.

  - Closing milestone tracker.

**Auditor Dashboard (Read-Only):**

  - Search: navigate by entity/transaction/user/date.

  - Audit trail viewer per entity.

  - Document access log.

  - Re-perform calculation interface.

## 5.2 Real-Time Refresh

Dashboard refresh strategy:

  - Critical metrics (saldo, posisi): refresh every 5 menit via polling atau WebSocket.

  - Aggregated views (CKPN, Stage Distribution): refresh on materialized view refresh (every 30 menit untuk hot data, daily untuk full).

  - Notifications: push real-time via SSE/WebSocket.

  - User-triggered refresh button untuk force update.

# 7\. Performance & Query Optimization

Reporting performance targets:

  - Standard report ≤ 10 detik (P95) untuk 1.000 instrumen.

  - Roll-forward 5-tahun history ≤ 30 detik (P95).

  - Dashboard refresh ≤ 5 detik (P95).

  - Excel export ≤ 60 detik untuk 10.000 rows.

**Optimization strategies:**

  - Materialized views untuk aggregate (refresh scheduled).

  - Read-replica DB untuk reporting queries (avoid OLTP impact).

  - Indexing: composite index pada (periode\_id, instrumen\_id), (counterparty\_id, evaluation\_date), dll.

  - Partitioning: tabel transaksi/audit by date range.

  - Caching: Redis untuk lookup dimensions yang frequent.

  - Pagination/streaming untuk large result sets.

  - Async export: untuk large export, generate file di background, notify user via email/in-app saat ready.
